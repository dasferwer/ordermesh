# Проверка OrderMesh

Проверено локально 29 сентября 2026 года на PostgreSQL 17 и RabbitMQ 4 в Docker Compose.

- Ruff: форматирование и статический анализ прошли.
- mypy: ошибок в 16 модулях приложения нет.
- Pytest: 19 тестов прошли.
- Восемь одновременных запросов с одним ключом создали один заказ и одно событие outbox.
- Ключи разных клиентов независимы; чужие заказы недоступны по ID и в списке.
- Параллельные дубликаты резервируют остаток один раз; изменённое событие отклоняется.
- Заказы с обратным порядком SKU не списывают больше доступного остатка.
- Конфликтующие конечные результаты не перезаписывают завершённый заказ.
- Ошибка записи outbox откатывает резерв и изменение остатка.
- Проверены аудит повторной отправки и сохранение ID и тела события.
- На реальном RabbitMQ проверены карантин, TTL-повтор и цепочка обработки результата.
  Неподтверждённая отправка не помечает outbox опубликованным; ошибка карантина не даёт ACK.
- В отдельных временных базах проверено обновление первоначальной схемы до текущей
  со сравнением исторических полей. Для исходной схемы подготовлены глобально
  уникальные ключи заказов; рабочие данные не изменялись.
- Полный стенд запущен, API и зависимости прошли healthcheck. Smoke-проверка создала
  заказ через HTTP и дождалась `fulfilled` от работающих workers. API использует UID 10001.

GitHub Actions повторяет статические проверки, тесты, миграцию, запуск и smoke-проверку.
Статус публикации определяется результатом workflow соответствующего коммита.

Не проверялись нагрузочная ёмкость, HA и восстановление резервных копий.
TTL/DLQ локального брокера не заменяют механизм автоматического восстановления
утраченных очередей. Границы доверия и ручной повтор описаны в архитектуре.
